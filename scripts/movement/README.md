# Проверки перемещений

После небольшой правки выполнять сборку и адресный сценарий. Длинную дорогу повторять при
изменении навигации/восстановления или новой причине для регрессии. Один полный реальный
прогон — после блока связанных изменений; полный цикл Zenthen с закупкой и возвратом
обязателен для приёмки этапа. Чистые таймеры проверять подстановкой возраста состояния.

Результат сценария автоматически собирать командой:

```sh
python3 scripts/movement/run_result.py TEST_CONTAINER 'SCENARIO ALL PASSED' \
  --timeout 180 --output /tmp/l2-movement-work/results/scenario
```

Сборщик принимает только контейнеры `l2-*` с `L2_MOVEMENT_ISOLATED=yes`, сохраняет полный
журнал и JSON с результатом/ID образа, завершает зависшее завершение процесса после результата.
Порты проверочного сервера не публиковать. БД восстанавливать только после завершения
предыдущего сценария. Для действительного длинного движения увеличить timeout по сценарию.

Переиспользуемые ситуации:

| Ситуация | Проверка | Что подтверждается |
|---|---|---|
| Нет денег/баланс изменился | `GatekeeperVerify`, `TravelBudgetVerify` | Нет поездки без реальной оплаты, сохранён запас неподготовленного персонажа |
| Недоступный путь | `MovementVerify`, `VillageExitVerify`, `StrandedWalkVerify` | Исключения, рампа и широкий обход с фактическим прибытием |
| Кончились расходники | `OfflineTownVerify`, `TravelBudgetVerify` | Срочная закупка и запрет траты защищённого резерва |
| Возврат после смерти | `OfflineDeathVerify` | Подстановка времени, настоящее воскрешение, городская зона, подход к торговцу и покупка |
| Включение без боя | `OfflineRetryVerify` | Неудачные маршруты забываются после опыта или конечного срока, не при одном включении |

Анализ живого журнала без изменений сервера:

```sh
docker compose logs --no-color --timestamps --since 1h game | python3 scripts/movement_report.py
python3 -m unittest discover -s scripts -p 'test_movement_report.py'
```

`MovementVerify.java` и `NavigationVerify.java` предназначены **только для отдельного сервера с копией БД**,
геодатой и выключенными населением/LLM. Они изменяют положение и состояние персонажей проверочной копии.
Не запускать в основном игровом процессе. `L2_MOVEMENT_ISOLATED=yes` — явный признак выбранного стенда,
а не автоматическая проверка изоляции.

Скомпилировать оба файла JDK 11 с библиотеками проверяемой сборки в classpath. На отдельном сервере
настроить JDBC на временную базу, `populationSize=0`, `llmNearProvider=off`, `llmFarProvider=off`.
Использовать копию с Zenthen, Weapons, BALiCTiK, Verzilas и INKOGNITO из исходного снимка.
Вместо обычного main-класса сервера запускать последовательно `MovementVerify`, затем `NavigationVerify`
с classpath библиотек игры и скомпилированных проверок. Порты стенда не публиковать.

- Первая проверка: реальные спавны, исключения неудачных спотов, задержка повторного поиска и возобновление.
- Вторая: лимит времени и прогресс маршрута, безопасные подходы к Papuma/Herbiel/Vollodos, фактический
  проход к торговцу, узкий поворот в Dark Elf Village и возврат офлайн-персонажа из Orc Village на спот.
- Для проверки только навигации на стенде персонаж получает GM-невидимость; бой этим тестом не проверяется.
- Успех — соответствующий маркер `MOVEMENT RETRY ALL PASSED` / `NAVIGATION ALL PASSED` и отсутствие
  `AssertionError`. **Кода выхода недостаточно:** shutdown hook ядра способен заменить код завершения JVM.

Эти проверки не заменяют наблюдение полной автоохоты на основном сервере и не доказывают доступность
всех направлений мира. Для найденной новой причины добавлять отдельный воспроизводимый сценарий.

Дополнительные последовательные проверки 02.11:

- `GatekeeperVerify` — местный учитель, отсутствие удалённого бесплатного телепорта из поля,
  пункты только из меню данного NPC, настоящая оплата через диалог, отказ при изменении баланса.
  Успех: `GATEKEEPER ALL PASSED`.
- `StatusVerify` — формат состояния молчащих ботов из снимка. Успех: `STATUS ALL PASSED`.
- `HuntRecoveryVerify` — снимок застрявшего Zenthen в Gludio (`-14056,121976,-2984`, lv 11,
  2196 аден). Должен найти путь за пределами первых пяти неудачных кандидатов. Режим
  `--plan-only` проверяет только выбор (`HUNT SEARCH ALL PASSED`). Обычный режим до 20 минут
  проверяет реальное движение и опыт без GM-защиты (`HUNT RECOVERY ALL PASSED`). Чтобы отдельно
  проверить поиск, необязательные городские дела и обучение в этой проверке отложены; это
  не приёмка полного цикла хозяйственных дел. Между проверками восстанавливать снимок БД.
- `TownPolicyVerify` и `OfflineTownVerify` — плановые дела после полезной охоты, срочное лечение
  без ожидания, отсутствие немедленной сдачи квеста после короткой охоты. Успех:
  `TOWN POLICY ALL PASSED` и `OFFLINE TOWN ALL PASSED`.
- `ReturnBudgetVerify` — заранее проверенный дальний возврат сохраняется после 5 минут,
  но ограничен рассчитанным конечным бюджетом. Успех: `RETURN BUDGET ALL PASSED`.
- `TravelBudgetVerify` — один SoE у новичка, дорожный бюджет только при готовом снабжении,
  реальное однократное списание за доступную охоту. Успех: `TRAVEL BUDGET ALL PASSED`.
- `VillageExitVerify` — точные позиции BlackForce и JetixmAX у тёмных эльфов, безопасные пути
  через узкую рампу; затем реальное движение BlackForce до охоты и прирост опыта. Навигация
  изолирована GM-невидимостью, для заключительного боя защита отключается. Прежняя сборка
  должна воспроизводимо отказать в пути BlackForce. Полный успех: `VILLAGE EXIT ALL PASSED`;
  `--plan-only` проверяет только планирование (`VILLAGE EXIT PLAN ALL PASSED`). Случаи sdf,
  Weapons и BALiCTiK требуют отдельного восстановления и этим сценарием не закрываются.
- `StrandedWalkVerify` — точная позиция sdf (`9123,23994,-3544`, lv 2): обычный выбор
  находит добычу, локальный путь отказывает, затем LifeBehavior должен сохранить намерение
  и выполнить проверенный обход около 50 тысяч единиц. До исправления проверка отказывает
  после первого отказа маршрута. Успех: `STRANDED WALK ALL PASSED`; `--plan-only` завершает
  проверку после установки и проверки обхода (`STRANDED WALK PLAN ALL PASSED`). Для движения
  используется GM-невидимость, для заключительного боя защита отключается. Бюджет стенда —
  до 17 минут на движение плюс 3 минуты на бой; это проверка восстановления, не полный цикл
  магазинов, квестов, отдыха и сессий.
- `IslandRecoveryVerify` — разовое исправление позиции трёх конкретных новичков с Primeval Isle
  на штатные стартовые точки класса 38. Проверяет сохранность уровня/опыта/аден/инвентаря,
  затем реальный опыт каждого через полные обычные обновления бота, без GM-защиты и ручного
  назначения добычи. Успех: `ISLAND RECOVERY ALL PASSED`. Ручная производственная коррекция
  записана в `repair-primeval-20261102.sql`, применяется только после остановки игры и бэкапа,
  в автоматическую инициализацию БД не включена. В ИИ свободный телепорт не добавляется.
- `OfflineRetryVerify` — включение/восстановление простоя сохраняют память неудачных целей;
  реальный XP снимает её, срок повторного поиска проверяется подстановкой времени.
  Успех: `OFFLINE RETRY ALL PASSED`.
- `HuntJourneyVerify` — общий срок между целями и участками, конечная пауза и применение
  в обоих контроллерах/ходоке. `--rules-only` не запускает мир и проверяет только время.
  Успех: `HUNT JOURNEY ALL PASSED` / `HUNT JOURNEY RULES ALL PASSED`.
- `KlockVerify` — сообщение/тип/место ошибки таймера, без игрового мира.
  Успех: `KLOCK DIAGNOSTICS ALL PASSED`.
- `OfflineBehaviorVerify` — свежий снимок с Zenthen и Afrodita, отсутствие боевого профиля
  после остановки и безопасное планирование сосок для воина/мага; отсутствие повторного
  запуска после передачи владельцу. Успех: `OFFLINE BEHAVIOR ALL PASSED`.
- `OfflineCycleVerify` — один полный цикл на свежем снимке текущего Zenthen: пустое место,
  город/дела, возвращение к охоте и XP **после выхода из города**, без выдачи денег/предметов,
  перемещения персонажа или GM-защиты. При необходимости подставляет возраст таймера
  пустого места и плановых дел после первого настоящего боя. Опыт за городской квест сам
  по себе успехом не считается. Завершается сразу по результату, предел сценария 25 минут.
  Успех: `OFFLINE CYCLE ALL PASSED`. Это один цикл, не подтверждение часовой устойчивости.
- `OfflineDeathVerify` — 242 нейтральные точки возврата из рабочего XML, ограниченная поправка
  высоты без смены XY/города, фактические возвраты в три деревни. Затем настоящая смерть,
  подстановка 16 секунд ожидания, воскрешение в распознаваемую городскую зону и реальная
  покупка хилки у Papuma без GM-защиты. Успех: `TOWN LANDING ALL PASSED` и
  `OFFLINE DEATH ALL PASSED`. Проверяется изменение точки прибытия; дальнюю дорогу этот
  сценарий не повторяет.
- `TownWalkVerify` — поле дальше 6000 от города, нет SoE и хилок, реальная дорога без GM,
  сохранность productiveSince на дороге, реальные закупки и намерение BACK_TO_SPOT.
  Срок определяется проверенным маршрутом и городскими делами, не только прямой дистанцией.
  Успех: `TOWN WALK ALL PASSED`.
- `TownSupplyCheckpointVerify` — продолжение сохранённого **городского** состояния из предыдущего
  сценария без повторения дороги; не восстанавливать исходную БД между этими двумя шагами.
  Завершает покупки, проверяет возврат и контракт неудачи/повторной попытки.
  Успех: `TOWN SUPPLY CHECKPOINT ALL PASSED`.
- `SupplyBudgetVerify` — чистый расчёт (`--rules-only`) и реальные NPC-покупки для офлайна и
  населения: ограниченный бюджет, ноль денег, лук с минимальными/дополнительными стрелами.
  Деньги/экипировка здесь задаются как условия торгового стенда; это не полный цикл персонажа.
  `--npc-only` позволяет воспроизвести старую политику без нового чистого правила.
  Успех: `SUPPLY BUDGET RULES ALL PASSED` / `SUPPLY BUDGET ALL PASSED`.

- `TownUnstuckVerify` — точный городской снимок Zenthen `-15048,124424,-3112`,
  подтверждение замкнутой геодаты, реальный собственный SoE и фактический подход к местному NPC;
  то же для бота населения. До запуска удалить **только на стенде** маркеры
  `character_offline_farm`: сценарий сам восстанавливает Zenthen из снимка до первого действия,
  чтобы исключить гонку с автоматическими городскими делами. Позиции/ресурсы Zenthen
  не задаются заново. Позиция/свиток населения — явно синтетические условия стенда.
  Обычный режим откладывает последующую охоту до окончания проверки подхода, без отмены возврата.
  `--no-scroll` удаляет только SoE в копии инвентаря, ждёт настоящий пятиминутный каст
  и проверяет реальный подход к местному NPC; внешний timeout не менее 430 секунд.
  `--hunt` дополнительно проверяет обычный выход на спот и настоящий XP без GM-защиты,
  с пределом дороги/боя 15 минут; смерть считается отказом. Полная версия первоначально
  воспроизвела смерть на первом споте. После повторной подготовки полный сценарий
  `RecoveryPreparationVerify` прошёл; `--hunt` теперь запускает именно его.
  Маркеры: `TOWN UNSTUCK ALL PASSED` / `TOWN UNSTUCK NO SCROLL ALL PASSED`.

  Маршрут к Bella от одного из случайных возвращений отдельно воспроизвёл `leg_changed`
  у `-14032,122952,-3112`. Сам сценарий восстановления его не закрывает; исправление
  отдельно принято проверками `NpcReturnVerify` и `LegChangeVerify`.

- `NpcReturnVerify` — точный вход к Harmony после городской смерти/возврата,
  проверка обратимости каждого звена, настоящая покупка за исходные деньги и пеший выход
  без SoE. Затем реальное прибытие по записанному пути Bella и проверка планов Papuma,
  Herbiel, Vollodos. Навигационные начальные позиции задаются только на копии;
  GM-защита не используется. `--plan-only` позволяет показать отказ прежней сборки
  на одностороннем подходе (`NPC RETURN PLAN ALL PASSED` для успеха).
  Полный маркер: `NPC RETURN ALL PASSED`, timeout 300 с.
- `NpcPopulationVerify` — фактический вход и пеший выход из того же магазина через
  актёра населения, без GM, выдачи денег и расхода SoE. Маркер:
  `NPC POPULATION RETURN ALL PASSED`, timeout 180 с.
- `LegChangeVerify` — после построения исходного луча однократно подставляет записанную
  в живом журнале промежуточную позицию `-14032,122952,-3112`. Это явно заданное условие
  навигационного стенда, не автоматический телепорт ИИ. Всё дальнейшее движение настоящее:
  прежняя сборка отказывает `leg_changed`, исправленная должна перестроиться и прийти.
  Маркер `LEG CHANGE ALL PASSED`, timeout 90 с.

- `RecoveryPreparationVerify` — реальный городской снимок Zenthen без подмены координат,
  денег и предметов: свой SoE, повтор обычных городских дел, покупка замены SoE,
  настоящие недостающие бафы у проводника новичков, выход и XP **после выхода из города**.
  Население отдельно воспроизводит преждевременно помеченную завершённой городскую подготовку;
  после настоящего восстановления этот признак должен быть снят. Только для этой
  дополнительной ситуации населения позиция/свиток задаются как условия стенда.
  `--prep-only` останавливается после реально полученных услуг; прежняя сборка до них
  начинала дорогу к охоте и воспроизводимо отказывает. Полный маркер:
  `RECOVERY PREPARATION ALL PASSED`, timeout 960 с.
- `TownUnstuckVerify` после добавления повторных городских дел изолирует сам механизм
  возврата отдельным владельцем действия, чтобы корректная новая закупка не нарушала
  прежнюю проверку «свиток израсходован/деньги не изменились». Полный `--hunt` направляет
  в `RecoveryPreparationVerify`. Обычный режим и `--no-scroll` сохраняют прежние маркеры.

- `ThinkingRecoveryVerify` — ошибка реального контроллера и отмена ожидаемого городского
  действия; оба раза после сбоя бот должен действительно выполнить следующее действие.
  Проверяется, что второй тик не освобождает чужой флаг и что отменённая последовательность
  не продолжает владеть актёром. Начальная позиция/кошелёк/запас населения задаются только
  на стенде для воспроизведения ожидания; GM-защита не используется. Маркер:
  `THINKING RECOVERY ALL PASSED`, timeout 150 с. Навигационная дорога повторно не нужна.

- `OfflineTravelRestartVerify --rules-only` — без запуска мира проверяет исходный срок
  охоты и сохранённую паузу через snapshot/restore, без ожидания таймеров.
- `OfflineTravelRestartVerify` — первый из двух настоящих запусков. Из исходного снимка
  Zenthen сам выходит из городской ловушки, получает обычные услуги и начинает пешую
  дорогу к добыче. После 300 реально пройденных единиц сохраняет контрольные данные
  `/verify/offline-travel-expected.properties`, вызывает обычную остановку и сохраняет актёра.
  Проверяет также все поля SQL-записи и отклонение неизвестной версии.
  Маркер `OFFLINE TRAVEL SAVED ALL PASSED`, timeout 660 с.
- Второй запуск `OfflineTravelRestartVerify --resume` использует **ту же БД и каталог /verify**.
  Между запусками нельзя восстанавливать дамп/удалять `character_offline_farm` или делать
  долгую паузу: исходный абсолютный срок дороги сохраняется. Обычный startup должен
  восстановить ту же цель, время, радиус, использованную поездку, бюджет и исключения;
  сначала фарм на промежуточной позиции запрещён. Дальше нужны физическое прибытие
  к исходной цели и настоящий XP. После этого проверяется очистка при новом активном
  задании и возврате владельца. Без GM, выдачи ресурсов и подмены позиции Zenthen.
  Маркер `OFFLINE TRAVEL RESUME ALL PASSED`, timeout 660 с.
- `OfflineTravelRestartVerify --seed-check` — короткая регрессия startup на заранее заданной
  записи дороги и маркере; предыдущая рабочая сборка игнорирует её и фармит промежуточную
  позицию. Подготовка этой ситуации изменяет только изолированную копию БД.
- `OfflineTravelOwnershipVerify` — конкурирующие завершение городского задания и вход
  владельца, затем запоздалое действие старого объекта при уже заменённой сессии.
  Здесь сама цель синтетическая, движение/бой не проверяются. Маркер
  `OFFLINE TRAVEL OWNERSHIP ALL PASSED`, timeout 90 с.

Новая таблица `character_offline_travel` добавляется при старте; схема также находится
в addon SQL патча. Записи завершённой дороги/возвращённого владельца удаляются. Обычные
шаги пути не пишут SQL; сохраняются этап, исходный срок и остановка сервера.

- `ThinkingDispatcherVerify` — регрессия настоящего таймера населения: ошибка до
  получения флага обработки не должна освобождать флаг другого вызова. Затем владелец
  отпускает флаг, и бот действительно выполняет следующее обычное действие (садится).
  Ошибка подставляется только в изолированном мире; её вывод проверяется и перехватывается,
  чтобы сборщик не принял ожидаемое исключение за отказ сценария. Без GM.
